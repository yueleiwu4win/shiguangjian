# 日有记 · 离线安卓技术方案 v0.1

方案日期：2026-10-25。对应《离线事记-v0.1.md》与已确认的古风竖向时间轴原型。

本文为待实施的技术设计；当前已完成需求与交互原型，尚未开发原生 App，也未测得文中性能指标。

## 1. 方案结论与边界

采用 **Kotlin + Jetpack Compose + Room + 应用私有文件存储**，开发单机原生 Android App。界面是古风手记，左侧时间轴串联当天事项，右侧显示正文和图片。

- 安装后无需账号或网络，可完成记录、图文浏览、日期查询、搜索、删除恢复、备份恢复。
- 一天多条事项；可补记；标题选填；正文与图片至少一项；每条最多 9 张图。
- 不建设服务器、接口、云数据库、账号体系或云同步服务。
- 本方案默认不做内容级加密、图片 OCR、拍照、视频、提醒或社交。应用锁与加密可另列版本，不能将应用私有存储称为已加密。
- Android 8.0 / API 26 作为建议最低版本，最终需结合目标手机确认；使用纯 Android API，不以 Google Play 服务为运行前提。
- compileSdk、targetSdk 与依赖版本在工程初始化时选择相互兼容的稳定版本，记录在版本目录并锁定；不在方案中预设“最新版本号”。开发机首次安装工具和解析依赖可能联网，与成品运行时完全离线分开。

## 2. 技术选型

| 范围 | 选择 | 在本项目中的用途 |
| --- | --- | --- |
| 语言 / 构建 | Kotlin、Gradle Kotlin DSL、Version Catalog | 原生工程，集中管理依赖版本 |
| 页面 | Jetpack Compose、Material 3 基础组件 | 自定义手记主题、时间轴、月历、图片网格 |
| 页面状态 | ViewModel、StateFlow、Coroutines | 单向数据流；数据库与文件操作离开主线程 |
| 导航 | 单 Activity + Jetpack Navigation（稳定 Compose 方案） | 记录、日历、详情、编辑、搜索、设置 |
| 数据库 | Room / SQLite | 事项、草稿、媒体索引、回收站、恢复去重记录 |
| 偏好设置 | DataStore | 主题、字号等小规模设置，不保存正文或图片 |
| 图片加载 | Coil 3 的 Compose 模块，按需 ExifInterface | 本地缩略图、大图采样与旋转，不引入网络加载模块 |
| 文件选择 | Storage Access Framework（SAF） | 用户选择本机图片、备份文件与导出位置 |
| 备份 | kotlinx.serialization + 流式 ZIP + SHA-256 | 跨版本逻辑备份、内容清单和完整性校验 |
| 测试 | JUnit、Room 测试、Compose UI 测试、真机验证 | 数据规则、迁移、恢复、核心交互与离线验证 |

架构采用 UI 层、数据层、Repository、ViewModel 与 Flow，与 Android 官方架构建议一致；小型项目先保持一个 app 模块，按包分层。来源：[Android 架构建议](https://developer.android.com/topic/architecture/recommendations)。

Coil 的网络能力通过独立模块提供，本项目只接入本地图片所需模块。来源：[Coil 官方组件说明](https://github.com/coil-kt/coil/blob/main/docs/getting_started.md)。

## 3. 应用结构

```text
Compose 页面
    ↓ 用户动作                     ↑ UiState
ViewModel（选择日期、编辑状态、错误反馈）
    ↓
Repository / 专项服务
    ├─ EntryRepository     事项查询、保存、删除、恢复
    ├─ DraftRepository     草稿落盘与恢复
    ├─ MediaStoreService   导入、缩略图、引用检查、垃圾清理
    ├─ BackupService       生成备份、校验、预览、合并恢复
    └─ SettingsRepository  主题、字号
    ↓
Room 数据库 / 私有图片文件 / DataStore
```

数据库是事项状态的唯一可信来源。页面监听查询结果，成功保存后由数据变更刷新时间轴，不在 UI 中维护第二套正式记录。

工程建议目录：

```text
app/src/main/
  java/.../daybook/
    app/                启动、导航、依赖容器
    ui/theme/           纸色、墨色、朱砂、字体与尺寸
    ui/components/      时间轴项、图片网格、日期切换
    ui/feature/         timeline/calendar/editor/detail/search/settings/trash
    data/db/            Entity、DAO、Migration
    data/repository/    事项、草稿、设置
    data/media/         文件导入、预览与回收
    data/backup/        格式、导出、校验、恢复
    model/              跨层数据类型与业务校验
  res/font/             随包字体及许可声明
  res/xml/              备份排除规则
```

依赖先通过轻量 AppContainer 和 ViewModel Factory 注入；复杂规则集中在保存、导入和恢复服务，不为每个查询添加一层空的 UseCase。

## 4. 数据模型

### 4.1 事项表 entry

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | UUID 字符串，主键 | 本机生成，供恢复去重 |
| entryDate | ISO 日期字符串 | 例如 2026-10-25；事项所属日期 |
| minuteOfDay | Int，0～1439 | 当天时间，可由用户修改 |
| title | String | 可为空 |
| body | String | 纯文本，保留换行 |
| searchText | String | 标题和正文规范化后的搜索副本 |
| createdAt / updatedAt | UTC epoch 毫秒 | 系统创建与修改时间 |
| revision | Long | 编辑版本，防止恢复或多编辑入口导致无提示覆盖 |
| deletedAt | 可空 UTC epoch 毫秒 | 不为空表示在回收站 |
| restoredFromId | 可空 UUID | 冲突恢复副本来源 |

默认排序：`entryDate DESC, minuteOfDay DESC, createdAt DESC, id DESC`。按天列表首先用所属日期过滤，回收站以 deletedAt 过滤。

索引建议：`(entryDate, deletedAt, minuteOfDay, createdAt, id)`；回收站另建 deletedAt 索引。月历通过日期范围内的分组计数查询获得，数据库不保存一份重复的“每天记录数”。

日期规则：所属日期使用 LocalDate，固定为用户选定的日期；创建时间使用 Instant。跨时区、跨零点不自动移动已经创建的事项。查询“今天”采用设备当前时区；不可选择未来日期。

### 4.2 媒体与草稿

| 表 | 关键字段 | 职责 |
| --- | --- | --- |
| media_asset | id、relativePath、sha256、mimeType、bytes、width、height、createdAt | 完整图片副本的文件索引；sha256 可设唯一索引用于内容去重 |
| entry_media | entryId、assetId、sortOrder | 事项与图片顺序，设置外键与顺序唯一约束 |
| draft | id、sourceEntryId、baseRevision、entryDate、minuteOfDay、title、body、updatedAt | 新建或编辑草稿；一条已有事项最多一个编辑草稿 |
| draft_media | draftId、assetId、sortOrder | 草稿对图片的引用 |
| restore_receipt | sourceRecordId、canonicalFingerprint、recordType、localRecordId | 识别已恢复的冲突版本，避免重复导入无限产生副本 |

图片文件以不可变资源处理：替换图片产生新资源，原资源在无事项、草稿、导入操作引用后才能清理。回收站事项仍保留引用。

业务约束由 Repository 在事务入口统一检查：图片最多 9 张、正文或图片至少一项、合法日期与时间。建议首版正文最多 20,000 字、标题 80 字，作为实现默认值，需在产品文案中明确。

## 5. 文件存储与图片处理

```text
应用私有目录/
  databases/daybook.db           Room 管理，同时可能存在 WAL / SHM
  files/media/<asset-id>.<ext>   图片完整副本，不能放 cache
  files/staging/<operation-id>/  导入与恢复中的临时文件
  files/backup-staging/          未完成的本地备份包
  cache/thumbs/                  可重新生成的缩略图
  files/datastore/               主题、字号等偏好
```

### 5.1 选择图片

首版使用 SAF `ACTION_OPEN_DOCUMENT`，MIME 限定 image/*，支持多选并设置 `EXTRA_LOCAL_ONLY=true`，请求系统返回设备上的本地内容；收到结果后再次检查数量、格式和可读取性。无需索取全部文件管理权限，也不依赖永久的相册 URI。

这里选择 SAF 是为了让离线约束与备份选择使用一致的系统接口。不同厂商文件选择器需实测本地筛选行为；不能仅因自己的 App 没有网络权限，就断言外部文件提供器不会访问网络。不可离线读取的文件导入失败并保留已有草稿，不等待后台云端下载。

依据：[SAF 文件访问](https://developer.android.com/training/data-storage/shared/documents-files)、[Intent.EXTRA_LOCAL_ONLY](https://developer.android.com/reference/android/content/Intent#EXTRA_LOCAL_ONLY)。

### 5.2 导入与存储默认策略

1. 通过 ContentResolver 流式复制到 staging，不把整个文件读入内存。
2. 检查实际文件签名、字节数和尺寸，不能只相信扩展名或提供器的 MIME。
3. 首版明确支持 JPEG、PNG、静态 WebP；其他格式给出清楚提示，HEIF、动画与 RAW 后续单独兼容。
4. 默认保留导入文件的完整字节，生成长边约 512px 的缩略图。原片策略避免初版出现不可逆画质损失，代价是占用空间较大。
5. 建议单图上限 25 MiB、约 50MP，作为防止意外巨图的可调整初始限制；解码前先读尺寸，并限制并发为 1～2 张。
6. 计算 SHA-256，文件移动到最终私有目录，再写入资产与草稿引用；显示成功前必须完成可恢复的引用落盘。
7. EXIF 方向在预览与大图渲染时统一处理；不要只旋转缩略图。原文件的拍摄元信息会随原片保留。

列表只加载缩略图，图片网格提前按尺寸占位，避免加载时把时间轴挤动。大图按屏幕采样，缩放级别设置合理上限，不把几十兆像素图片一次性完整解码。

### 5.3 数据库与文件的一致性

文件系统与 SQLite 无法组成同一个原子事务，使用“先写文件，后提交引用”原则：

- 在同一应用内部文件系统内完成临时文件写入、关闭与移动后，再提交 Room 事务。
- 数据库提交成功前不向用户显示已保存；事务失败时保留草稿，遗留文件由回收流程处理。
- 崩溃可能留下没有引用的文件，但不应产生已提交记录指向尚未写入的文件。
- 清理前检查 entry_media、draft_media 和当前操作引用；仅对超过保护期且确认无引用的资源删除。初始保护期可设为 24 小时。
- 永久删除先在事务中移除记录和引用，再异步清理不再被引用的文件；失败可重试，不阻断其他记录。
- 所有资源变更、恢复和清理通过同一单写入协调器串行化，避免清理与保存竞争。

## 6. 草稿与保存流程

编辑态由 ViewModel 持有，草稿通过 DraftRepository 持续写入 Room。

- 输入停止约 500ms 后落盘，并设置持续输入时最多约 2 秒写入一次，避免纯防抖一直不保存。
- 返回、切换页面、应用进入后台时请求一次尽力落盘；不能把 onStop/onDestroy 当作必定执行的保障。
- 恢复的是最近一次已成功写入的草稿，不宣称强制杀进程时零字符丢失。界面显示“草稿已保存”需对应实际成功写入。
- 图片导入完成时立即更新草稿引用；图片处理中不能提交正式事项。
- 保存动作先等待在途草稿写入结束，并读取最新编辑快照。通过单写入队列和版本号防止旧的防抖任务在保存后重建草稿。
- Room 事务内写事项、替换图片关联、更新 revision，并移除对应草稿；成功后返回所选日期。
- 编辑已有事项时校验 baseRevision。若正式事项已变化，保留当前草稿并提示冲突，不悄悄覆盖。
- 保存失败留在编辑页，正文与图片保留，给出可重试的错误。

`SavedStateHandle` 只保留日期、事项 ID、滚动位置等轻量状态；正文和图片不放入 Bundle 作为唯一副本。

## 7. 页面实现与古风设计

### 7.1 时间轴

- 使用 LazyColumn，一条记录一个稳定 UUID key；左列约 52～60dp 显示时间，右列展示内容。
- 时间、节点与标题首行对齐，使用每条记录自己的实际测量高度绘制线段。首项从节点向下，末项由顶部到节点，中间项上下贯通；单项只画节点。
- 线段覆盖条目内部留白，条目之间不额外插入会断开连接线的间距；不用一张固定高度的大 Canvas 覆盖整个列表。
- 正文与图片高度可变；稳定 key、图片尺寸占位和可恢复的 LazyListState 防止返回详情后跳位。
- 1 张图较大展示，4 张图为 2×2，其余最多 3 列；图片网格最多 9 张，用普通 Row/Column 或自定义 Layout，不在滚动列表内部嵌套纵向滚动网格。
- 屏幕阅读器按“日期、时间、标题、正文、图片数量”读取；轴线和装饰印记不参与朗读。

稳定 key 与惰性列表的实现依据：[Compose 列表文档](https://developer.android.com/develop/ui/compose/lists)。

### 7.2 古风主题

- 统一设计 token：宣纸底、墨色正文、淡褐分隔、朱砂主操作；深色模式使用对应色组。
- 标题、题签使用随 APK 打包且许可允许分发的中文字体；正文优先使用系统清晰字体。字体授权与文件大小在实现时检查，保留许可声明。
- 不依赖手机是否安装楷体，也不在线下载字体；纸纹用轻量本地纹理或绘制方式实现，不使用整屏超大位图。
- 标题有古风，但按钮仍使用“保存、返回、搜索、删除”等明确文字。
- 支持系统字号与应用字号组合；时间列、操作区和日期选择器在大字号下可重排。主要触控区域至少 48dp。

### 7.3 日历与搜索

- 月历用本地日期计算，周一开头；月份切换后查询该月计数，选日后复用时间轴组件。
- 日历的未来日期禁选，但显示完整月份；点击今天恢复设备本地日期。
- 搜索首版采用规范化标题/正文的子串匹配，支持中文片段，参数化查询并用约 300ms 输入防抖取消旧请求。
- 可使用 `instr(searchText, :query) > 0` 配合日期范围与删除状态过滤，结果分页；普通 B-tree 索引不被当作正文包含搜索的加速方案。
- 空关键词展示符合日期条件的全部记录；日期起止不合法时先提示，不执行错误查询。
- 初版不引入中文分词或依赖默认 FTS 分词行为满足中文子串搜索。若目标数据量下实测过慢，再评估 n-gram 索引或专门的中文检索方案。

## 8. 回收站

移入回收站仅设置 deletedAt，事项与图片继续存在。正式列表、月历和普通搜索均排除已删除事项。

- 恢复：清除 deletedAt，回到原日期。
- 永久删除：明确确认后移除事项和关联，再按资源引用清理图片。
- 首版不自动定时清空，避免用户误解保留期限。
- 若该事项有编辑草稿，删除时一并转为不可提交状态或要求用户先处理；不允许旧草稿无提示将已删除事项重新创建。

## 9. 备份与恢复

### 9.1 逻辑备份格式

导出 `.daybook` 文件，内部为 ZIP 容器：

```text
manifest.json        formatVersion、导出时间、应用版本、文件清单、计数、SHA-256
entries.jsonl        事项，包括回收站状态
drafts.jsonl         草稿及源事项版本
relations.jsonl     事项/草稿与资源的有序关联
media/<id>.<ext>     完整图片副本
```

缩略图不备份，恢复后重建。业务内容与可选显示偏好分开；首版不覆盖当前设备显示偏好。

备份包版本与 Room schema 版本独立。采用逻辑导出避免直接复制正在写入的数据库、遗漏 WAL，或把某版 SQLite 结构作为唯一可恢复格式。

首版备份默认未加密，SHA-256 用于发现损坏，不是加密或身份认证；导出说明应准确告知文件包含完整记录和原图片。若后续加入密码备份，需要单独设计密码派生、认证加密和找回边界。

### 9.2 导出流程

1. 先落盘当前草稿，再进入单写入协调区。首版备份期间允许浏览，暂时禁用保存、删除、导入和清理。
2. 在一致的逻辑快照上导出 JSONL，流式读出不可变图片，生成本机 staging 备份包；不持有覆盖整个文件复制过程的数据库长事务。
3. 对照清单核对所有文件、记录数与引用，保证缺图不会被当成成功备份。
4. 用户通过 SAF 选择本地存储目的地，写入已经校验的包。可读取的目的地重新打开比对大小/摘要；关闭与写入失败不得标成功。
5. 写入成功后更新上次成功备份时间并展示文件位置。失败时保留可重试状态，尽力移除不完整目标文件。

SAF 外部提供器不保证原子覆盖，因此每次创建新文件，不覆盖用户之前的成功备份；本机临时包验证完成不等同于外部导出已成功。

### 9.3 恢复流程与冲突规则

1. 用户选文件，先复制进本机 staging，后续校验使用这份固定副本。
2. 验证格式版本、JSON 类型/长度、文件数量、SHA-256、图片格式与关联完整性；限制解压总体积与压缩比，拒绝路径越界、重复路径和未知目标路径。
3. 显示预览：可新增、可跳过、冲突副本、回收站事项、草稿数量，以及所需空间。用户点击确认恢复。
4. 获得单写入锁后重新计算当前数据的冲突计划，再提交；避免预览期间数据改变而造成错误覆盖。
5. 新资源先写入完整且不可变的正式资源文件；随后在 Room 事务中整体合并事项、草稿、关联和去重凭据。
6. 事务失败保持原有业务数据，清理本次未引用资源；成功后异步重建缩略图。

冲突规则：

| 情况 | 行为 |
| --- | --- |
| 原 ID 不存在 | 导入，保留原 ID 和所属日期 |
| 原 ID 存在且规范化内容相同 | 跳过 |
| 原 ID 存在但内容不同 | 保留本机，给导入版本生成新 ID，标记恢复副本 |
| 相同冲突版本重复导入 | 根据 restore_receipt 跳过，避免重复生成副本 |
| 图片内容相同 | 按摘要与大小复用已验证资源，仍保留各自展示顺序 |

规范化内容指纹包括正文、标题、事项日期/时间、删除状态和有序图片摘要；不包含本机生成的副本名称、ID 或导入时间。草稿执行同类冲突处理；源事项版本不一致时作为可独立保存的恢复草稿，不能直接覆盖原事项。

### 9.4 大文件与中断

- 备份和恢复使用流式文件处理，禁止把全部图片或完整 ZIP 载入内存。
- 预估本机临时空间、解压空间、最终新增资源及数据库 WAL 开销；不能只按压缩文件大小判断是否足够。
- 首版为前台长操作，提供进度、取消与返回提示；应用进程被终止时本次未提交操作失败，已有数据不受破坏。
- 重启识别遗留 staging 并清理或提示重试。若后续需要离开页面后继续数 GB 操作，再加入符合目标 Android 版本约束的持久任务调度；不把 WorkManager 用作草稿保存的唯一保障。

## 10. 离线约束与系统配置

1. 最终合并后的 Manifest 中不得出现 INTERNET 权限；构建校验覆盖依赖带入的权限。
2. 不接入广告、统计、远程崩溃上报、在线字体、远程配置或自动检查更新。
3. 配置 `allowBackup=false`，并为适用 Android 版本维护备份排除规则，排除数据库、图片、草稿和设置的云备份与设备传输。
4. 不能只依赖 allowBackup：官方说明部分厂商设备的设备间传输有差异，发布前实机验证；采用手动备份作为明确支持的数据迁移方式。
5. 日记正文、图片路径和搜索词不写入生产日志；诊断只保留错误类型与不含内容的操作标识。
6. 文件只通过用户主动选择的 SAF URI 导出；无宽泛文件权限、定位、联系人或后台常驻服务。

系统备份规则及厂商差异依据：[Android Auto Backup 文档](https://developer.android.com/identity/data/autobackup)。

## 11. 版本升级与交付

- Room schema 导出进版本库，每次数据库变更提供明确 Migration，并测试旧版到新版的真实数据升级。
- 禁止使用会在缺少迁移时清空日记数据的 `fallbackToDestructiveMigration`。
- 未支持的较新备份格式明确拒绝，保留原文件与本机数据；旧格式按备份迁移器转换。
- 发布 APK 使用固定包名和可持续保管的签名证书。签名密钥由项目所有者保管并备份，不能将其提交进源码仓库；后续覆盖安装升级保持签名一致。
- 提供测试 APK、发布 APK、源码、构建说明、备份格式说明与验收记录。APK 不代表自动上架应用商店。

数据库迁移行为依据：[Room 迁移文档](https://developer.android.com/training/data-storage/room/migrating-db-versions)。

## 12. 测试与性能目标

以下是待验证目标，不是已完成的性能承诺。建立固定基准手机和 Release 构建，数据集先覆盖 10,000 条记录与 5,000 张图片。

| 范围 | 核心验证 |
| --- | --- |
| 业务规则 | 图文至少一项、图片上限、日期补记、跨日编辑、稳定排序、回收站过滤 |
| 草稿 | 持续输入、暂停、返回、进程终止、旧保存任务迟到、图片导入中断 |
| 图片一致性 | 删除相册源图后可读；导入失败无坏引用；EXIF 方向；巨图不 OOM |
| 备份恢复 | 空库恢复一致；重复导入去重；冲突副本幂等；包含草稿和回收站 |
| 故障注入 | 无剩余空间、半写文件、损坏 ZIP、路径越界、校验失败、各提交阶段杀进程 |
| 数据升级 | 每条迁移路径上的正文、图片引用、删除状态与日期不丢失 |
| UI | 单条/多条时间轴连续；单图/4图/9图；深色、横屏、大字号、返回位置 |
| 离线 | 飞行模式完成核心全流程；抓取 Manifest 与依赖审计结果；无 Google 服务真机 |
| 性能目标 | 基准机冷启动可交互约 2 秒内；按天数据查询 p95 约 100ms 内；搜索 p95 约 500ms 内（不含输入防抖）；滚动无明显卡顿 |

兼容覆盖最低版本、Android 12/13 及当前目标版本，并至少覆盖两类厂商真机；输入法、文件选择器和系统恢复行为是实机重点。

## 13. 实施顺序与工作量估算

假设由 1 名熟悉 Kotlin / Compose 的开发者完成，原型方向稳定，不包含应用商店审核、额外加密、多端同步或大幅视觉返工。预计 **20～29 个工作日**，工程初始化和真机可用后再细化。

| 阶段 | 内容 | 可验收产物 | 估算 |
| --- | --- | --- | --- |
| 1 | 工程、主题、数据库、基本事项读写 | 可安装，古风时间轴显示本机文字记录 | 3～4 天 |
| 2 | 图片导入、网格、大图、草稿 | 图文记录闭环，重启后数据完整 | 4～6 天 |
| 3 | 日历、搜索、编辑、回收站 | 历史查询与内容管理闭环 | 3～4 天 |
| 4 | 备份包、校验、恢复、去重与失败处理 | 跨设备手动迁移，重复恢复可验证 | 5～7 天 |
| 5 | 迁移/故障测试、真机适配、性能与发布签名 | 验收通过的首版 APK 与源码 | 5～8 天 |

最先交付“可安装的文字时间轴”，再补完整图文和数据保护。排期中需给备份恢复和异常测试保留独立时间，不能只以界面完成度判断项目完成。

## 14. 开发前可采用的默认决策

当前方案可按以下默认值开工设计，无须重新讨论已确认的页面方向：

- 最低 Android 8.0；纯原生、无后端。
- 每条 9 张图；原片保留＋缩略图；图片格式与大小限制见第 5 节。
- 新到旧时间轴；标题选填；本地子串搜索。
- 手动完整备份，默认合并恢复；首版备份不加密。
- 应用锁、内容加密、图片 OCR 与提醒延后。

若目标设备低于 Android 8.0，或日记必须加密，应在工程落地前调整兼容范围或存储设计。字体文件、签名归属、备份扩展名和包名在工程初始化时定稿。
